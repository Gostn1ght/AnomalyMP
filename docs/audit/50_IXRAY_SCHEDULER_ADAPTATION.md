# 50. Адаптация планировщика IX-Ray (2026-10-07)

Запрос владельца: продолжать этапы и адаптировать scheduler IX-Ray, сохраняя
численность, поведение и частоту обновления NPC/мутантов GAMMA. Нативные сборки
и исполнение C++ проверок выполняются только в GitHub Actions.

## Источник и границы заимствования

Сверены официальные исходники ixray-team/ixray-1.6-stcop:

- [stable, 612b165c](https://github.com/ixray-team/ixray-1.6-stcop/blob/612b165c97d5e6a50ac0a6d1384ac8c95a63dda5/src/xrEngine/xrSheduler.cpp);
- [develop, c55dacab](https://github.com/ixray-team/ixray-1.6-stcop/blob/c55dacab6165c0f28fd09479043fcd89a9625357/src/xrEngine/xrSheduler.cpp);
- dev/IxAiStack, 7e9368b81137d49dfedecaa84bab5edb76b8b483.

Основной алгоритм уже совпадал с Lost Zone: realtime список, heap обычных
объектов, интервал через shedule_Scale и адаптивный бюджет. Эти версии IX-Ray
не дают готового параллельного выполнения GAMMA Lua/ИИ. Замена названия
планировщика сама по себе не решает кадр 110 мс при 64 игроках рядом.

Адаптированы profiling scope из develop и допустимый повторный unregister
из stable. Поверх этого реализована безопасная отмена и ускорена обработка
пакета регистраций. Оригинальные stable cpp/h и полная лицензия сохранены в
scripts/fixtures/ixray-scheduler. Уведомление включается в DX11 artifact:
notices/IX-Ray-LICENSE.md.

## Реализация

- Парные register/unregister сопоставляются за ожидаемое O(n), вместо
  вложенного поиска и erase из середины массива. Правило «первый register —
  первый следующий unregister того же указателя» сохранено.
- Каждая активная регистрация получает поколение. Удаление объекта и создание
  нового по тому же адресу не оживляет старую запись heap/realtime очереди.
- Отмена обычного объекта не сканирует heap. Неактивные записи пропускаются,
  когда наступает их время, без обращения к уничтоженному объекту.
- Массовая отмена realtime объектов выполняет одну stable compaction после
  пакета, вместо полного прохода по списку на каждую отмену. Если отмен не было,
  лишний проход для compaction вообще не выполняется.
- Удаление себя или соседнего объекта внутри shedule_Update/Needed/Scale
  не сдвигает realtime массив во время обхода; следующий живой объект получает
  своё обновление. EnsureOrder внутри callback применяется после обхода.
- ISheduled.b_RT инициализирован для никогда не зарегистрированных объектов.
- Сохранены исходные t_min/t_max, расчёт Scale, dt clamp обычных объектов,
  realtime dt, heap comparator, проверка бюджета и его сглаживание. Изменение
  t_max внутри Scale учитывается в dt, как в исходном алгоритме.
- Callback ИИ остаётся в исходном игровом потоке. Нет сокращения population,
  частоты binders, числа целей игроков или лучей зрения.

## Проверка и критерии приёмки

scripts/check-netcoop-scheduler.py компилирует настоящий xrSheduler.cpp и
ISheduled.cpp вместе с закреплённым IX-Ray baseline. Подмена только host services:
Device, часы/CPU, строки и отладочные функции; сами алгоритмы не переписаны в тест.
profiler.h копируется из настоящего xrCore; PROF_EVENT не подменяется в host.
Baseline переименован для совместной линковки; литерал 1000i64 преобразован в
равнозначный 1000LL для GCC. Реализация проверяется MSVC и GCC, release/DEBUG;
GCC дополнительно использует AddressSanitizer и UndefinedBehaviorSanitizer.

Проверки:

1. 10 000 случайных пакетов регистраций против исходного quadratic pairing;
   пакет 50 000 объектов / 100 000 запросов с полным взаимным исключением.
2. 64 realtime + 128 обычных объектов, 500 разных кадров: точное совпадение
   порядка, времени вызова, dt и итогового бюджета с IX-Ray. Включены пропуски
   Needed для realtime, перерегистрация, длительные кадры и изменение t_max
   внутри Scale.
3. Удаление себя/другого объекта, отмена в Needed/Scale, повторное использование
   адреса, отложенный EnsureOrder без пропуска живого realtime объекта;
   дополнительный пакет 2048 realtime отмен со stable compaction.
4. Полная DX11 сборка и упаковка клиента/сервера в GitHub Actions.

Следующий этап без ухудшения ИИ: искать повторные чистые чтения данных в Lua/С++
по inclusive профилю сталкеров и кэшировать по точным версиям зависимостей.
bind_script_actor уже разрешает Lua functor один раз; вложенная привязка акторов
уже переиспользуется через depth, повторять этот кэш не нужно. В CPropertyStorage
есть линейный поиск, но m_storage открыт для внешних записей: простой кэш без
аудита этих записей некорректен. Результаты Lua evaluators нельзя считать чистыми
без проверки их зависимостей и побочных эффектов.
Общие результаты зрения разных NPC нельзя переиспользовать без равенства
начала/конца луча, маски, исключений и ревизии геометрии.
