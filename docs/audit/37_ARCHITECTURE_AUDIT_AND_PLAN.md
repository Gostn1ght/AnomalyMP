## 2. Как устроено сейчас

```
Клиент (bin/AnomalyGammaNetClientDX11)          Выделенный сервер (dedicated/...Server)
 рендер, HUD, UI, звук, ввод                     CLevel + xrServer (один уровень онлайн)
 свой актор: движение, HUD-предметы  --M_CL_*--> ALife-симулятор ВСЕХ уровней (офлайн)
 NPC = марионетки (позиция/анимации) <--M_UPDATE-- объекты уровня, NPC-ИИ, Lua GAMMA
 Lua GAMMA (UI/эффекты, без ALife)   <--события-- аккаунты, деньги, торговля, диалоги,
                                                  задания на игрока, погода
```

- Транспорт: DirectPlay, один процесс сервера, один уровень «онлайн», ALife
  симулирует остальные уровни абстрактно (офлайн-сквады).
- Репликация: каждый кадр `SendUpdatesToAll` — все онлайн-объекты уровня
  (`net_Export`) всем клиентам, частота `psNET_ServerUpdate = 30`.
  **Нет AOI**, кроме ALife switch distance (онлайн/офлайн вокруг игроков ≈150 м).
- ID сущностей: `u16` (≤ 65535 на весь мир).
- Lua: одно состояние на процесс, однопоточное; весь геймплей GAMMA там.

## 3. Какие системы есть / отсутствуют / singleplayer-only

Есть и работают на сервере: ALife, NPC-логика GAMMA (биндеры, схемы, смарты),
мутанты, аномалии (серверные зоны), выдача заданий, диалоги (серверный прогон,
клиент только окно), торговля и деньги, аккаунты/роли, погода (выбор на сервере).

Есть, но только одиночные по природе (singleplayer-only), и уже частично
адаптированы: `db.actor` (один игрок), `Actor()`, `AC_ID`, сохранения,
`task_manager`, эмиссии/пси-шторм, `SIMBOARD` в UI, GAMMA-колбэки `actor_on_*`,
level changer (переход = перезагрузка уровня у всех).

Отсутствуют: AOI/приоритизация, дельта-сжатие по полям, lag compensation
(отмотка хитбоксов), несколько уровней одновременно на одном сервере,
межсерверный перенос игрока, постоянное хранилище мира (кроме аккаунтов и денег),
античит сверх валидации событий, метрики/профилировщик сервера,
боты для нагрузочных тестов.

## 4. Честная оценка цели «512 игроков»

- Один процесс X-Ray держит **один онлайн-уровень** и весь ALife. Узкие места:
  однопоточный Lua (GAMMA тратит основную часть кадра на скрипты NPC),
  полная репликация без AOI, DirectPlay (устаревший, ограниченная
  пропускная способность и масштаб), `u16` ID.
- Реалистично на одном процессе-локации после оптимизаций: **десятки игроков
  (ориентир 16–32)**, число подтвердит бенчмарк. 512 на один процесс
  в X-Ray+GAMMA недостижимо без переписывания Lua-геймплея.
- 512 на **мир** возможны только как «много процессов-локаций» (как в ТЗ),
  но в X-Ray ALife глобален (сквады ходят между уровнями), поэтому нужен
  отдельный слой: каждый процесс-локация симулирует свой уровень онлайн,
  а межуровневая симуляция и перенос сущностей — через общий сервис мира.
  Это крупный проект (месяцы), а не правка.

## 6. Целевая архитектура (поэтапная, без «большого переписывания»)

```
                 [клиенты]
                     |
            [шлюз / логин-сервис]  (аккаунты, роли, выбор локации)
                     |
      +--------------+---------------+
      |              |               |
 [локация Болота] [локация Кордон] ... каждая = отдельный dedicated X-Ray
      |              |               |   (свой онлайн-уровень, свой Lua, AOI)
      +------[сервис мира]-----------+
              (межуровневый ALife/сквады, перенос игроков,
               хранение игроков и мира, погода/выбросы мира)
```

Ключевые решения и компромиссы:
1. **Остаёмся на X-Ray и Lua GAMMA** — иначе теряем весь контент. Всё новое
   делаем в движке (C++) и тонком Lua-оверлее.
2. **AOI и приоритизация** внутри `xrServer::SendUpdatesToAll`: клиент
   получает объекты в радиусе и с частотой по дистанции. Это главный рычаг
   трафика и основа для десятков игроков на локации.
3. **Транспорт**: DirectPlay заменить на современный UDP-транспорт
   (например, ENet/GameNetworkingSockets) за тем же интерфейсом
   `IPureServer/IPureClient`. Отдельный этап, после AOI.
4. **Локации как процессы + сервис мира**: перенос игрока между процессами
   (сериализация актора и инвентаря, как `M_NETCOOP_*`), общий ALife — через
   сервис мира. Самый дорогой этап, делать последним.
5. **Персистентность**: сначала файловые снапшоты игрока (инвентарь,
   здоровье, задания, деньги — рядом с `netcoop_accounts.txt`), затем
   вынос в сервис хранения (SQLite/PostgreSQL — выбрать при реализации).

## 8. Риски

- Lua GAMMA рассчитан на одного `db.actor`: каждая система требует адаптации
  (сейчас — привязка ближайшего игрока, per-player задания).
- DirectPlay: предел масштабирования, нестабильность под нагрузкой.
- ALife глобален — разделение по процессам затрагивает ядро симуляции.
- `u16` ID и формат пакетов X-Ray — смена потребует миграции.
- Сборка только в CI (≈25 мин на итерацию) — замедляет отладку.

## 9. План бенчмарков

Метрики сервера (этап 3): время кадра, доля Lua, ИИ, физики, репликации,
байт/с на клиента, число онлайн-объектов. Сценарии: 1/2/8/16/32 бота на
Болотах, бой рядом с базой, выброс. Сеть: RTT 20–250 мс, потери 0–5 %.
