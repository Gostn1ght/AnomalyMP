# Native checkpoint worker — M2b subtask

`CheckpointWorker` connects the durable outbox to a bounded, thread-safe producer boundary and actual WinHTTP execution. The translation unit is included in xrGame with exceptions enabled and precompiled engine headers disabled. The engine-facing header contains fixed-size POD metadata only: no JSON, credentials, Lua or game object pointers. Public calls contain exceptions; start/stop require other callers to be quiesced, and submit/poll/release/status may otherwise run concurrently.

## Ownership and progress

The future admission coordinator must provide an already owned location scope: world/seed/epoch/location/instance/fence and validated character session/entity/save versions. The worker only renews that lease. It never claims a location, creates/resumes an entity, takes over a session, runs migrations or enables primary gameplay persistence. Existing installed character loading/saving stays on its verified local path until admission/hydration/world-inventory coordination is complete.

Config and journal IO happen after asynchronous start on the pump thread, including recovery of queued metadata and persistent generation floors. A separate renewal thread maintains the existing lease while the pump is doing filesystem IO. Lost renewal replies retain the original command ID AND original send time, so a cached acknowledgement cannot extend the local lease deadline. Permanent/malformed authority responses seal the scope; transient failures retry while the local deadline controls readiness. Every checkpoint/renewal request carries the same expected world/seed/epoch and instance. No automatic re-claim occurs.

Submission owns an independent NCH image and returns memory acceptance only. A shared budget of 32 captures / 64 MiB includes buffered captures, durable spool entries and unconsumed receipts, with a 20 MiB maximum image and one transient staging copy. The persistent identity/generation history remains bounded to 5120 entries. Recovered jobs are Staged, never Durable, until a fresh Finish proof. Per-character capture versions/generations remain ordered, and a rejected job blocks later jobs of that character without discarding their data. Other characters are served round-robin, one HTTP step at a time, with retry delay. No producer performs filesystem/HTTP work.

Receipts include generation/revision/entity version/bytes/SHA and `latest_submitted`. This flag includes newer captures accepted into the memory mailbox even when disk admission has not completed. A gameplay handoff must additionally compare/freeze the coordinator's newest captured generation, verify current worker readiness/ownership and coordinate all inventory/world mutations. `release` is an asynchronous local retirement request only after the coordinator consumes/persists that exact durable receipt; disappearance from the initialized worker confirms index retirement. `generation_floor` seeds capture counters after restart/retirement.

Shutdown stops admission/network pumping and stages accepted memory locally; it does not wait for every master upload. A false stop result requires coordinator recovery/fallback. In-flight synchronous filesystem IO can delay thread joining; no bounded filesystem latency or game-shutdown acceptance is claimed. The source change introduces no new live game caller or automatic writer activation.
