# 106 — Отдельный EXE мастера, по этапам

Требование владельца: отдельная консоль запуска мастера, логи, EXE; основная
БД сохранений игрока находится в мастере, включая положение/состояние и задания
между локациями. Не выдавать существующий HTTP/backend прототип за интеграцию
всех сохранений в движок. H09/H11 и следующие пункты остаются OPEN до проверки.

## M0: упаковка и жизненный цикл консоли

Подготовлен `backend/master_entry.py` поверх существующего мастера. EXE содержит
код и Python runtime, но не содержит runtime/config.json, токенов и БД.
Режимы и аргументы существующего сервиса сохраняются. Без аргументов EXE открывает
консоль с `runtime/config.json` рядом с самим EXE; конфигурацию первоначально
создаёт настройка хостера. Существующую конфигурацию не перегенерировать.

`serve` и `console` пишут UTF-8 лог в `logs/master.log` рядом с конфигурацией;
`--log-file` задаёт другой путь. Лог дописывается, старые строки не удаляются.
ANSI оформление консоли не попадает в файл. Строки с именами чувствительных
полей удаляются из файлового лога целиком; незаконченные строки буферизуются,
чтобы значение токена из следующего write не утекло. Ошибки приватной
конфигурации выводятся только названием класса исключения.

Локально прошли реальные процессы `init`, `console`, `status`, `quit`, SQLite,
путь с пробелами и отсутствие сгенерированных ключей в stdout/stderr/логе.
Первый тест обнаружил UnicodeEncodeError Windows pipe для символов консоли;
stdio entry переведено в UTF-8, повторный тест успешен.
Полный набор backend: 292 теста, 84.9 секунды, успешно.

Windows EXE собирает отдельный CI job после всей проверки backend на Linux и
Windows. Smoke test запускает именно собранный EXE, без внешнего Python у него
в аргументах. Артефакт: `LostZone-Master-Windows`, EXE, SHA256 и исходный commit.
Нативный движок локально не собирается.

Упаковщик PyInstaller 6.16.0 закреплён; используется готовый bootloader wheel,
`--onefile --console --noupx`, без данных runtime. Опции проверены по
[официальной документации](https://pyinstaller.org/en/v6.16.0/usage.html).
CI `38574136828` завершён успешно: 292 backend теста на Linux и Windows,
пакетирование и smoke именно EXE. Проверка скачанного EXE локально также прошла.
SHA256: `b41e0cf59b56702059e4d375f5d88505119215d011e5f8e588b0974cf29462f8`.
Первый запуск `38573005529` не создал jobs: YAML plain scalar команды pip
содержал `: ` в `--only-binary=:all:`. Переведено в literal block, YAML проверен
локальным parser. Успешные backend тесты не означают готовый EXE до нового CI.

### M0: установка и контроллер хостера

EXE из `d2f4d8983` установлен в `hoster/master` тестового сервера и комплекта
`J:\LostZone_Work\Lost Zone Server`. Существующие runtime/config.json, БД и
ключи не копировались и не изменялись. Резервный переносной Python сохранён.
Контроллер и панель предпочитают EXE, удаляя только Python-префикс `-m lostzone`
из прежних CLI-вызовов. Консоль запускается своим видимым окном; отдельный
`Start Master.cmd` запускает мастер без карт. Короткие init/export скрыты.
Поиск процессов сравнивает точные пути EXE, включая оба процесса onefile,
и не затрагивает соседние каталоги мастера или посторонний Python.

`check-netcoop-master-packaged.ps1` прошёл на Windows PowerShell 5.1 и PowerShell 7
с настоящим CI EXE в временном пути с пробелами без Python fallback: init,
экспорт bridge/writers, повторная инициализация без изменения config,
запуск HTTP на выделенном тестовом порту, поиск и остановка собственных
процессов, SQLite и лог без сгенерированных секретов. Fixture добавлен в CI
упаковщика. Отдельно argv fixture проходит на обеих версиях, включая настоящий
Unicode: исправлена ошибочная вложенная JSON array проверка в PS 5.1, а не CLI.

M0 реализован, проверен на настоящем EXE и установлен. Это не закрывает M1–M3
и перенос основного native player save в БД мастера.

## M1: контракт и миграция сохранений

Следующий этап: сопоставить account + slot/character ID, WorldID/seed, location
и revision между native .bin и записью мастера. Зафиксировать полный состав
сохраняемого состояния (инвентарь/UID, здоровье, деньги, положение, прогресс,
инфопоршни, задания, состояние поведения). Снять резервную копию и проверить
контрольные суммы перед импортом. Некорректный файл не заменять пустой записью.

## M2: мастер как основной источник player save

После проверки миграции переключить запись/чтение движка на мастер с fencing
локации, идемпотентным commit и подтверждением durable записи до освобождения
персонажа/перехода. Проверить logout/login, перезапуск мастера и локации,
отключение сети, stale writer, дубликат и падение между save и transfer.
До переключения существующие native сохранения остаются источником восстановления.

## M3: задания и торговля

Исправить настоящий путь диалога/ассортимента/выдачи задания, затем связать
передачу прогресса с durable character commit мастера. Проверить Кордон ↔ Болота
одним клиентом: задание выдано, прогресс продолжен на другой карте, награда
выдана один раз, состояние переживает выход и перезапуск.

### M1: проверка и архивирование native player save

Реализованы bounded NCH3..8 parser, identity WorldID/seed/account/slot, read-only dry-run и атомарный staged импорт в schema5 SQLite. Четыре существующих NCH8 проверены без изменения. Контракт и точные границы — doc 109. Импорт не создаёт live entity/session и не переключает native restore; M2 и M3 открыты. Новый EXE и CI ещё требуется подтвердить.
