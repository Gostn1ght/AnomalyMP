# 38 — План: идеальная синхронизация и плавность, путь к 512 игрокам

Дата: 2026-09-28. Статус: **на утверждение владельцем**. Дополняет док 37
(архитектура) и док 36 (разбор эталона «Lost Path Online / Anomaly COOP»).

## 1. Почему сейчас всё дёргается (причина, а не симптомы)

Жалобы: NPC ходят боком, телепортируются и дёргаются; игрок дёргается и
откатывается; торговцы стоят боком; NPC стреляют без причины; игра не плавная.
Это не отдельные баги скриптов, а один слой — сетевое ядро:

1. **NPC обновляются редко и рывками.** Сервер кладёт снимок NPC
   (`uNext` в `CAI_Stalker::shedule_Update`) только в тик планировщика:
   100–250 мс по конфигу, а под нагрузкой GAMMA — реже. Клиент
   интерполирует с задержкой `NET_Latency` = 50 мс (`xrServer.h`), то есть меньше
   интервала между снимками. Клиент почти всегда экстраполирует, а при
   приходе нового снимка прыгает к нему: это и есть «телепорт и дёрганье».
2. **Нет единого тика и меток времени сервера на снимок.** Позиция, поворот
   тела, анимации и слот приходят разными путями и в разные моменты. Отсюда
   «боком»: поворот тела берётся из одного источника, анимация движения из
   другого.
3. **Свой игрок: жёсткие коррекции вместо согласования.** Клиент предсказывает
   движение, сервер при расхождении присылает позицию, и клиент прыгает
   (пороги 8 м). Нет буфера вводов с номерами и повторного применения
   (reconciliation), поэтому бывает откат.
4. **Состояние NPC неполное.** Эталон передаёт одним пакетом: позицию,
   скорость, тип движения, тело, ментальное состояние, слот, предмет,
   дорожки анимаций torso/legs, состояние оружия, strap и действие. У нас —
   часть этого, по разным каналам.
5. **Стрельба NPC без причины**: вероятно, оружие марионетки проигрывает
   выстрелы по состоянию оружия без цели от сервера, либо серверный NPC
   реально стреляет по невидимому для клиента игроку-актору. Нужен лог
   выстрелов на сервере (кто, в кого) — этап 0.

Вывод: латать по одному симптому бесполезно, нужен новый сетевой слой
состояния (этап 1). Всё остальное — поверх него.

## 2. Реверс эталонного движка: что реально, а что нет

- **Целиком декомпилировать и перенести — нереально.** EXE 37 МБ, C++ без
  исходников. Декомпилятор даёт не компилируемый код, а псевдо-C. Перенос
  всё равно был бы переписыванием, только вслепую.
- **Точечный реверс — да.** По строкам лога (`[COOP NPC] Runtime captured`,
  `Local apply`, `HIT BRIDGE`, `SHOTFX`) находятся конкретные функции
  (Ghidra), по ним восстанавливаются формат пакета и логика применения
  (интерполяция, сглаживание поворота). Для этапа 1 это нужно сделать для
  двух мест: NPC runtime packet и применение на реплике.
- **Lua эталона (77 тыс. строк `_COOP_*`) читается напрямую** — это готовые
  решения для синхронизации мутантов, квестов, анимаций предметов, чата/отряда.
- **Самый дешёвый путь**: попросить у автора не весь исходник, а 3–4 файла
  (`CoopRemoteActorManager.cpp`, файлы NPC runtime/replica из
  `xrGame\coop\`). Это экономит недели реверса.
- Во всём, что взято из эталона, указываем авторство (док 36).

## 3. Про 512 игроков честно

- Эталон рассчитан на кооп (в конфиге `max_player ≤ 255`, на практике
  единицы игроков). Он **не** решает задачу 512.
- Один процесс X-Ray + Lua GAMMA на одной локации: реалистично десятки
  игроков (цель 32–64 после AOI и оптимизаций, подтвердить нагрузочным
  тестом).
- 512 на **мир** — только шардинг: каждая локация отдельный серверный процесс,
  общий сервис мира (межуровневый ALife, перенос игрока, хранение). Это
  этапы 5–6. Без этапов 1–4 шардинг даст 512 дёргающихся игроков.

## 4. Этапы (каждый с измеримым критерием)

| Этап | Что делаем | Критерий готовности |
|---|---|---|
| 0. Измерения (1–2 дня) | Метрики сервера (тик, Lua, ИИ, сеть), на клиенте — лог интервалов снимков, числа экстраполяций/прыжков на объект, ошибок коррекции актора; лог выстрелов NPC на сервере. Автотест: 2 клиента, маршрут игрока, наблюдение за NPC. | Базовые цифры до изменений |
| 1. Сетевое ядро плавности | (а) фиксированный тик снимков сервера (30 Гц) с меткой серверного времени и номером; (б) буфер интерполяции на клиенте для всех удалённых объектов (NPC, мутанты, другие игроки): задержка ≈ 2 интервала снимка, ограниченная экстраполяция, сглаживание поворота; (в) свой актор: номера вводов, повторное применение после ответа сервера, мягкая коррекция вместо прыжка; (г) единый пакет состояния NPC по образцу эталона, поворот тела и головы раздельно. | 0 прыжков > 0.3 м у NPC в радиусе 50 м при RTT 100 мс; нет откатов игрока при беге; торговцы стоят как во фриплее |
| 2. Паритет с фриплеем на Болотах | Диалоги, торговля (покупка/продажа), ПДА, задания на игрока, выбросы/пси-штормы, метки карты, лут, смерть/респавн. Чек-лист + автотесты. | Чек-лист из ТЗ на 2 клиентах |
| 3. Масштаб локации | AOI (радиус и частота по дистанции), приоритеты, дельта-сжатие полей, headless-боты. | Нагрузочные тесты 8/16/32/64, P95 тика |
| 4. Транспорт | Замена DirectPlay на GameNetworkingSockets (Valve, открытый; его же использует эталон) за интерфейсом `IPureServer/IPureClient`. | Бенчмарк до/после, потери 0–5 % |
| 5. Локации-процессы | Отдельный сервер на локацию, переход игрока между процессами, сервис мира. | Болота → Кордон между процессами |
| 6. 512 на мир | Сервис мира, хранение, мониторинг, восстановление. | Soak-тест с ботами |

Точечный реверс эталона идёт параллельно с этапом 1 (формат NPC-пакета
и применение на реплике), Lua эталона — с этапом 2.

## 5. Решения, нужные от владельца

1. Модель авторитета (док 37, §10): **A** — выделенный авторитетный сервер
   (соответствует ТЗ и античиту, рекомендуется) или **B** — как эталон, ИИ NPC
   у ближайшего игрока.
2. Попросить ли у автора эталона 3–4 исходных файла NPC/реплик вместо реверса.
3. Утвердить старт с этапов 0 → 1.

## 6. Решения владельца (2026-09-28)

1. **Модель A с приоритетом плавности**: сервер — авторитет (защита), но
   клиент обязан выглядеть как одиночная игра: предсказание своего игрока,
   буфер интерполяции для всех чужих объектов, мягкие коррекции. Защита и
   плавность — оба обязательны, компромисс «в пользу одного» не принимается.
2. **Реверс эталона делаем сами** (точечно, Ghidra + строки лога + их Lua).
3. **Старт: этап 0 → этап 1.**
4. **Мастер-сервер вместо «просто отдельных серверов»**: над серверами
   локаций стоит мастер-сервер, который владеет глобальным состоянием и
   синхронизирует его во все локации и всем игрокам: игровое время, погода,
   выбросы и пси-штормы, глобальные события (новости, межуровневые сквады,
   экономика/торговцы, аккаунты, деньги, хранение игроков). Серверы локаций
   подчиняются его часам и событиям. До появления нескольких процессов
   (этап 5) эти функции живут в модуле «мастер» внутри текущего сервера с
   тем же интерфейсом, чтобы потом вынести его в отдельный процесс без
   переделки.
